## План интеграционного тестирования

<a id="test-1-manual-integration-test-developer"></a>
### Тест 1: ручная интеграционная проверка разработчиком

**Предварительные условия:**
```bash
# Build backend
cd d:\GitHub\skymp\skymp5-server
npm ci && npm run build

# Build frontend
cd d:\GitHub\skymp\skymp5-front
npm ci && npm run build
```

**Порядок проверки:**
1. Запустить сервер с поддержкой WebSocket.
   ```bash
   cd d:\GitHub\skymp\build
   ./launch_server.sh  # or launch_server.bat on Windows
   ```

2. Открыть административную панель.
   - Перейти на http://localhost:7777/admin либо использовать настроенный порт.
   - Открыть инструменты разработчика браузера → Network → WS.

3. Проверить WebSocket-соединения.
   - Убедиться в подключении к `/ws/admin-updates`.
   - Состояние: ✅ OPEN, зелёный индикатор.
   - Во вкладке сообщений должны регулярно появляться данные.

4. Проверить состояние и игроков в реальном времени.
   - Ожидается: изменения состояния появляются сразу, менее чем за 100 мс.
   - Прежний опрос: 5000 мс.
   - Улучшение: **в 50 раз быстрее**. ⚡

5. Проверить поток журнала.
   - Перейти на вкладку Logs.
   - Ожидается: новые записи появляются в реальном времени.
   - Резервный опрос при отсутствии WebSocket: 5 с.

6. Проверить поток событий.
   - Перейти на вкладку Events.
   - Ожидается: новые события восстановления появляются сразу.
   - Пример: возрождение игрока вызывает рассылку события.

7. Проверить обновления возрождения.
   - Перейти на вкладку Respawn.
   - Ожидается: список поверженных игроков обновляется в реальном времени; резервный опрос 3 с.

8. Проверить историю.
   - Открыть History в верхней панели.
   - Ожидается: новые административные действия появляются в реальном времени; резервный опрос 5 с.

9. Проверить резервный режим.
   - Отключить WebSocket-сервер или закрыть соединение.
   - Наблюдать попытки повторного подключения в консоли браузера.
   - Ожидается: автоматический переход к HTTP-опросу.
   - Задержка: 1 с → 2 с → 4 с → … → 30 с, экспоненциальное увеличение.

<a id="test-3-performance-validation"></a>
### Тест 3: проверка производительности

**Измерение задержки:**

| Тип обновления | До (HTTP) | После (WebSocket) | Улучшение |
|-------------|---------------|-------------------|------------|
| Состояние | ~5000 мс | ~50 мс | В 100 раз |
| Игроки | ~5000 мс | ~50 мс | В 100 раз |
| Записи журнала | ~5000 мс | ~50 мс | В 100 раз |
| События | ~5000 мс | ~50 мс | В 100 раз |
| Записи истории | ~5000 мс | ~50 мс | В 100 раз |
| Состояние возрождения | ~3000 мс | ~30 мс | В 100 раз |

**Потребление памяти:**
- Пул WebSocket: примерно 5 МБ на 50 одновременных клиентов.
- Буфер сообщений: пренебрежимо мал.
- В оригинале как расход памяти указано: менее 1 % CPU.

**Сетевой трафик:**
- Опрос: 1 запрос/5 с × 60 с = 12 запросов/мин на точку.
- WebSocket: 1 соединение и периодические сообщения, в среднем около 1 КБ/с.
- Экономия: **на 95 % меньше HTTP-запросов**.

<a id="test-4-fallback-reliability"></a>
### Тест 4: надёжность резервного механизма

**Сценарий 1: WebSocket недоступен при запуске**
- Ожидается: HTTP-опрос включается сразу.
- Пользователь не видит ошибок.
- Панель полностью работоспособна.

**Сценарий 2: WebSocket-соединение потеряно**
- Ожидается: автоматическое повторное подключение с экспоненциальной задержкой.
- Максимальное ожидание: 30 с.
- Действия пользователя не нужны.

**Сценарий 3: разрыв сети**
- Ожидается: контролируемый переход к опросу.
- После восстановления связи обновления продолжаются.
- Потери данных нет.
