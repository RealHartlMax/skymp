# План системы нескольких персонажей

> План/исследование, проверено 22 октября 2026 года. Предложения и примеры внешних fork не означают реализацию в этом checkout. Подтверждённое выполнение см. в [статусе проекта](docs_project_status.md) и основной дорожной карте.

<a id="goal"></a>

## Цель

Реализовать готовый к эксплуатации поток, в котором игрок:

1. Один раз аутентифицируется аккаунтом.
2. Видит экран выбора персонажа.
3. Выбирает существующего или создаёт нового.
4. Появляется в мире выбранным персонажем.

Система остаётся серверно-авторитетной и защищённой от подделок клиента.

<a id="current-baseline"></a>

## Текущая основа

- Вход существует и отправляет `spawnAllowed` с `profile.id`.
- Появление автоматически выбирает только первого актёра профиля.
- При отсутствии актёра персонаж создаётся неявно.
- Клиентский вход уже поддерживает custom packet и UI браузера.

<a id="scope"></a>

## Объём

<a id="in-scope"></a>

### Входит

- Получение и отображение списка.
- Пакет выбора и проверка.
- Пакет создания и серверный путь создания.
- Появление явно выбранного персонажа.
- Настраиваемый предел персонажей профиля.
- Минимальные журналы администратора/телеметрии.

<a id="out-of-scope-initial-version"></a>

### Не входит (первая версия)

- Средства смены имени.
- Платные дополнительные слоты.
- Подробный косметический предпросмотр.

<a id="architecture"></a>

## Архитектура

<a id="data-model"></a>

## Модель данных

Хранить метаданные в записях актёров (`mp.set(...)`), например:

- `private.charName: string`
- `private.charSlot: number`
- `private.createdAt: number` (unix ms)
- `private.lastPlayedAt: number` (unix ms)

Не доверять метаданным клиента. Сервер вычисляет канонический список по актёрам, связанным с `profileId`.

<a id="server-events-and-packets"></a>

## Серверные события и пакеты

<a id="server---client"></a>

### Сервер → клиент

- `characterList`
  - `characters: Array<{ actorId: number; name: string; level: number; slot: number; lastPlayedAt?: number }>`
  - `canCreateNew: boolean`
  - `maxCharacters: number`

- `characterSelectRejected`
  - `reason: string`

- `characterCreateRejected`
  - `reason: string`

<a id="client---server"></a>

### Клиент → сервер

- `selectCharacter`
  - `actorId: number`

- `createCharacter`
  - `name: string`

<a id="security-rules-must-have"></a>

## Обязательные правила безопасности

1. При `selectCharacter` проверить наличие `actorId` в `ctx.svr.getActorsByProfileId(profileId)`.
2. Отклонять отключённых, удалённых или неверных актёров.
3. При `createCharacter` проверять на сервере:
   - максимальное число
   - формат и длину имени
   - уникальность имени, если включена
4. Не принимать клиентские `profileId`, уровень, инвентарь.
5. Перед окончательным появлением повторно проверять соединение/пользователя (`ctx.svr.isConnected(userId)`).

<a id="integration-plan"></a>

## План интеграции

<a id="phase-1---server-core"></a>

### Этап 1 — ядро сервера

Целевые файлы:

- `skymp5-server/ts/systems/spawn.ts`
- Новый: `skymp5-server/ts/systems/characterSelect.ts`

Задачи:

1. Изменить spawn listener, чтобы при нескольких персонажах не выбирать `[0]` автоматически.
2. Отправлять `characterList` при `actors.length > 0`.
3. Сохранить прямое создание, если актёров нет.
4. Добавить `characterSelect.ts` для `selectCharacter` и `createCharacter`.
5. Подключить после входа, до окончательной передачи появления.

Критерии приёмки:

- Профиль с 2+ актёрами получает список вместо немедленного появления.
- Корректный `selectCharacter` выбирает нужного актёра.
- Неверный выбор отклоняется с явной причиной.

<a id="phase-2---client-flow"></a>

### Этап 2 — клиентский поток

Целевые файлы:

- `skymp5-client/src/services/services/authService.ts`
- Модуль выбора frontend: новый компонент `skymp5-front` или существующий webview входа

Задачи:

1. Обрабатывать `characterList` и показывать UI.
2. По нажатию отправлять `selectCharacter`.
3. Через «Создать» отправлять `createCharacter`.
4. Блокировать повторную отправку при ожидании.
5. Показывать причины отказа.

Критерии приёмки:

- Выбор существующего персонажа через UI.
- Создание нового ниже лимита.
- Корректное восстановление UI после отказа/таймаута.

<a id="phase-3---character-metadata-and-ux"></a>

### Этап 3 — метаданные и UX

Задачи:

1. Сохранять/обновлять `private.lastPlayedAt` после появления.
2. Сортировать список по слоту или последней игре.
3. При небольших затратах добавить уровень/локацию.

Критерии приёмки:

- Детерминированный порядок списка.
- Обновление последней игры при входе.

<a id="phase-4---hardening-and-observability"></a>

### Этап 4 — усиление и наблюдаемость

Задачи:

1. Структурированные журналы успехов выбора/создания и отказов.
2. Ограничение частоты `createCharacter` на пользователя.
3. Счётчики:
   - list_shown
   - select_success
   - select_reject
   - create_success
   - create_reject

Критерии приёмки:

- Типичные злоупотребления отклоняются и журналируются.
- Есть эксплуатационные метрики для внедрения.

<a id="server-settings"></a>

## Настройки сервера

Добавить блок в `server-settings.json`:

```json
{
  "characterSystem": {
    "maxCharactersPerProfile": 5,
    "nameMinLength": 3,
    "nameMaxLength": 24,
    "namePattern": "^[A-Za-z0-9 _'-]+$",
    "enforceUniqueNames": false,
    "createCooldownMs": 3000
  }
}
```

Значения по умолчанию должны быть безопасны и обратно совместимы.

<a id="backward-compatibility-strategy"></a>

## Обратная совместимость

1. При отсутствии `characterSystem` использовать значения по умолчанию.
2. Для одного актёра при желании автопоявление до завершения внедрения UI (флаг).
3. Сохранить старое офлайн-поведение, если явно не включено.

Предлагаемый флаг:

- `characterSystem.enabled: boolean` (по умолчанию `false` для поэтапного внедрения)

<a id="test-plan"></a>

## План тестирования

<a id="unitintegration"></a>

### Модульные/интеграционные

1. `selectCharacter` принимает ID своего актёра.
2. Чужой ID отклоняется.
3. `createCharacter` отклоняется при лимите.
4. Неверное имя отклоняется.
5. Успешное создание появляется в новом списке.
6. Отключение между списком и выбором не обрушает сервер.

<a id="manual-qa"></a>

### Ручная проверка

1. Первый вход без персонажей: создание работает.
2. Возвращающийся игрок с тремя: показан список.
3. Подделка чужого `actorId`: отказ.
4. Спам создания: лишние запросы ограничены.

<a id="rollout"></a>

## Внедрение

1. Поставлять с `characterSystem.enabled=false`.
2. Включить на staging.
3. Проверить журналы, метрики, хранение.
4. Постепенно включать на рабочих серверах.
5. Удалить временную совместимость после стабильного периода.

<a id="risks-and-mitigations"></a>

## Риски и меры

- Гонки при асинхронном выборе/создании.
  - Мера: повторно проверять соединение и владение перед окончательной привязкой.

- Несогласованные старые актёры без метаданных.
  - Мера: резервные значения (`name="Unknown"`, `slot=actorId`).

- Рассинхронизация пакета и UI.
  - Мера: авторитет сервера; клиент повторно запрашивает список при несоответствии.

<a id="definition-of-done"></a>

## Критерии готовности

1. Можно выбирать из нескольких персонажей профиля.
2. Неавторизованный выбор невозможен на сервере.
3. Лимиты и проверки действуют.
4. Поток покрыт автоматическими тестами и ручным списком.
5. Документация и справочник настроек обновлены.
