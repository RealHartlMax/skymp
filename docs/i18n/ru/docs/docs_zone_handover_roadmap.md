# Дорожная карта передачи зон и маршрутизации инстансов

> План/исследование, проверено 22 октября 2026 года. Предложения и примеры внешних fork не означают реализацию в этом checkout. Подтверждённое выполнение см. в [статусе проекта](docs_project_status.md) и основной дорожной карте.

Документ предлагает эксплуатационный поток передачи при переходах локаций (города, помещения, подземелья) за загрузочными экранами Skyrim.

Цели:

- Сохранить социальность MMORPG: игроки по умолчанию встречаются в одних местах.
- Повысить масштабируемость и изоляцию сбоев.
- Подготовить дополнительные overflow-shard для переполненных мест.

<a id="design-principles"></a>

## Принципы

1. Общие зоны по умолчанию

- Одинаковый мир/ячейка означает общее социальное пространство.
- Не делать частные инстансы каждого игрока стандартом.

2. Техническое разделение ради производительности

- Симуляция зоны может работать отдельными worker/процессами.
- Это разделение выполнения, а не игровая изоляция.

3. Контролируемые дополнительные shard

- Создавать копии зоны только при превышении вместимости.
- По возможности сохранять участников группы в одном shard.

<a id="why-loading-screen-is-the-right-handover-point"></a>

## Загрузочный экран как точка передачи

Экран загрузки уже означает жёсткую смену сцены. Он предоставляет безопасное и прозрачное для пользователя окно для:

- снимка состояния
- передачи владения
- инициализации целевой зоны
- детерминированного подтверждения завершения

Это уменьшает визуальные артефакты и гонки при движении/бое.

<a id="proposed-handover-workflow"></a>

## Предлагаемый поток

<a id="phase-1-pre-handover-source-zone"></a>

### Этап 1: подготовка исходной зоны

- Клиент запрашивает переход.
- Исходный worker блокирует актёра на время передачи.
- Создаёт авторитетный снимок:
  - трансформация и worldOrCell
  - параметры актёра и смерть/возрождение
  - изменения инвентаря/экипировки
  - активные эффекты и выбранные флаги выполнения
- Публикует токен и данные маршрутизатору/хранилищу.

<a id="phase-2-transfer-routing"></a>

### Этап 2: передача и маршрутизация

- Маршрутизатор выбирает целевой worker/shard по:
  - ключу назначения
  - заполнению и состоянию shard
  - правилам привязки группы
- Целевой worker проверяет токен и создаёт/загружает состояние актёра.
- Исходный сохраняет резервирование до целевого ACK.

<a id="phase-3-post-handover-target-zone"></a>

### Этап 3: завершение в целевой зоне

- Целевой worker отправляет появление/телепорт.
- Клиент выходит из загрузки только после ACK готовности.
- Исходный очищает данные после подтверждения commit.

<a id="consistency-and-safety-requirements"></a>

## Согласованность и безопасность

1. Идемпотентность

- Повторный запрос входа не создаёт двойного актёра.
- Токен одноразовый.

2. Атомарная смена владения

- Актёр принадлежит либо источнику, либо цели, никогда обоим.

3. Таймаут и откат

- Без целевого ACK источник восстанавливает актёра и отменяет передачу.

4. Гарантии порядка

- Отбрасывать старые пакеты движения/боя прежней эпохи владения.

5. Наблюдаемость

- Считать задержки, сбои, повторы и откаты.

<a id="integration-points-in-current-skymp-architecture"></a>

## Точки интеграции текущей архитектуры

Текущая реализация показывает подходящие границы:

- Единый контейнер мира:
  - `skymp5-server/cpp/server_guest_lib/PartOne.h` (`WorldState worldState`)
- Основной цикл тиков симуляции:
  - `skymp5-server/cpp/server_guest_lib/PartOne.cpp` (`worldState.Tick()`)
- Ключ границы локации в протоколе:
  - `skymp5-server/cpp/messages/TeleportMessage.h` (`worldOrCell`)
- Обработка несовпадения мира/ячейки клиентом:
  - `skymp5-client/src/sync/movementApply.ts`

Это подходящие точки разделения router/worker с сохранением поведения игры.

<a id="suggested-incremental-rollout"></a>

## Постепенное внедрение

<a id="milestone-1-protocol-and-transfer-state"></a>

### Веха 1: протокол и состояние передачи

- Добавить токен и эпоху владения в движение/телепорт.
- Добавить блокировку передачи у источника.
- Базовый таймаут и откат.

<a id="milestone-2-router-and-worker-abstraction"></a>

### Веха 2: абстракции router/worker

- Ввести интерфейс маршрутизатора.
- Сначала один процесс с логическими worker.
- Проверить сквозные инварианты тестами.

<a id="milestone-3-multi-worker-deployment"></a>

### Веха 3: несколько worker

- Отдельные процессы для выбранных зон.
- Dashboard метрик и оповещения сбоев.
- Проверка повторного соединения во время передачи.

<a id="milestone-4-optional-overflow-shards"></a>

### Веха 4: дополнительные shard

- Адаптивное создание для переполненных мест.
- Соблюдение привязки группы и социальной целостности.
- Общий shard по умолчанию при нормальной нагрузке.

<a id="non-goals-for-initial-implementation"></a>

## Не входит в первую реализацию

- Частные инстансы каждого игрока как стандарт
- Бой между shard в первой версии
- Полное распределённое переписывание до доказательства корректной передачи

<a id="acceptance-criteria-mvp"></a>

## Критерии приёмки (MVP)

- Вход в помещения/подземелья использует детерминированный transfer.
- Нет двойного владения после перехода.
- Неудачная передача безопасно откатывается без потери игрока.
- p95 задержки под нагрузкой приемлема; порог определить в эксплуатационном руководстве.
- Общее социальное поведение при нормальном онлайне сохранено.
